# Allocator-war lead acquisition launch Wave 23 method

Wave 23 converts the fifty-two Wave 22 queue tasks into an initial acquisition front without pretending that queue admission is evidence acquisition. Every one of the eleven estate queues contributes exactly one lead packet. The selector orders tasks by `P0`, `P1`, then `P2`, and resolves a same-priority tie by the lowest source-task sequence. It does not use actor prominence, political salience, anticipated conclusion, apparent culpability, or editorial preference.

The result is a bounded cross-estate launch set. Ten queues contribute a `P0` denominator, universe, inventory, correction, appeal, litigation, roster, or outcome task. The intellectual-property, standards, and data-rights estate has no `P0` task, so its first `P1` instrument-and-rights task is admitted. This fallback follows the declared selector rather than creating an exception for that estate.

Each packet retains the source queue, source task, reviewed and unreviewed authority references, task authority, required output, closure test, allowed result states, controls, refusals, and blocked promotions. Reviewed routing remains below second-party review. Split routing keeps reviewed and unreviewed sources distinguishable. Unreviewed routing authorizes acquisition only.

The retrieval contract is official-first. A later executor must retain an exact source locator, issuing body, source type, jurisdiction, bounded window, retrieval date, content hash or stable official identifier, coverage statement, included and excluded rows, nulls, unavailable rows, refusals, and correction route and outcome. Negative search and failed paths remain part of the result rather than disappearing from the denominator.

Wave 23 attaches estate-specific source families so that a task can move directly into acquisition without a new interpretive sorting step. Source-family assignment is a routing aid. It is not a source receipt, evidence review, legal-entity resolution, relationship, recurrence finding, prevalence estimate, or publication clearance.

No result ledger is created in this wave. Every packet is `ready_for_acquisition`, carries zero result rows, and remains unadjudicated. A later execution wave must write separate packet-specific result ledgers and may return supported, contradicted, mixed, no-observed-effect, unavailable-after-search, or outside-bounded-window. None of those states independently promotes an estate finding or changes the graph.

Ancestry validation is portable across full-history checkouts and depth-one pull-request merge checkouts. When the declared base commit is absent in GitHub Actions, the validator fetches `GITHUB_HEAD_REF` into an explicit remote-tracking ref and tests the same ancestry predicate against that recovered feature-branch tip. Missing ancestry after targeted recovery and genuine non-ancestry remain blocking.
