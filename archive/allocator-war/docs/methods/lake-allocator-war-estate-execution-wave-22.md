# Allocator-war estate acquisition execution — Wave 22

Wave 22 converts the eleven estate referrals admitted by Wave 21 into deterministic acquisition queues. It does not acquire the external records itself and it does not promote an estate finding. Its job is to make the next evidentiary work executable, ordered, source-addressed, and fail-closed.

Each Wave 21 estate feed remains the queue key. Every `next_acquisition` item becomes one task with a stable `task_ref`, source authority, required output, closure test, allowed terminal states, retained controls and refusals, and explicit blocked promotions. The transformation preserves the source feed’s reviewed-only, split-authority, or unreviewed-acquisition-only state.

Priority is an execution ordering, not a truth, merit, risk, guilt, or importance score.

```text
P0  denominator, affected population, option universe, correction, appeal, or final outcome
P1  operative criteria, custody, terms, rights, selection, rejection, exception, or review instrument
P2  longitudinal performance, failure, recurrence, substitution, exit, recovery, or null control
```

The first matching priority class wins. Every task remains bounded by the estate consumer question and the source route. A task may terminate as supported, contradicted, mixed, no observed effect, unavailable after search, or outside the bounded window. None of those states self-promotes into the estate, compact, racial-order, prevalence, coordination, or common-purpose layers.

The queue compiler preserves the following constitutional distinctions:

```text
reviewed routing is below second-party review
split routing does not launder unreviewed intake
unreviewed intake authorizes acquisition only
controls and refused inferences travel with supportive material
queue recurrence does not establish prevalence
same consumer does not create a relationship
graph effect: none
publication: blocked
```

Wave 22 uses the existing allocator-war source, lake-action, and report basins. Exact file paths are added to those basins. No new semantic basin, identity, relationship, participation, active claim, hop, finding, or publication authority is created.

Ancestry validation distinguishes an unavailable commit object from failed ancestry. Wave 21 custody checks may add several independent depth-one boundaries to a pull-request checkout, which makes `--unshallow` fail because the shallow file changes during recovery. The validator therefore retries only when the initial predicate cannot be proved, fetching `GITHUB_HEAD_REF` into an explicit remote-tracking ref at depth 1,000,000 and rerunning the same merge-base ancestry test against that recovered feature-branch tip. The repository may remain formally shallow, but the complete head-to-checkpoint path is present. A checkpoint missing after targeted deep-history recovery or a recovered non-ancestor remains blocking.
